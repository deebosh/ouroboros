# Managed Update Rule

Managed update binds targets and owns writer admission, local-work custody, resolver authority and recovery of the live tree.

- Local work branch and official feed stay separate; topology: ARCHITECTURE §8 (`ouroboros/update_channels.py`).
- Preflight selects one exact target. Apply binds base/target, closes new writers, drains direct turns, stops workers/services and re-plans before mutation. Write the transaction first; reopen only after verified abort/rollback or healthy restart. Delayed evolution cleanup uses the same update lock/admission owner.
- Conversation and repo-writing differ. Destructive apply/replace/rollback/materialization refuses turns; while the authorized assisted resolver owns `assisted_resolution`/`committing_assisted`, Main answers but other tasks’ repo tools remain refused. Steering uses ordinary `steer_task`; admission lives in `worker_chat_lane.conversation_admitted_during_update`. `preload_owner_control_path` imports server packages before conflict markers enter the materialized checkout.
- Dirty work never enters merge history: stash it, then restore it uncommitted. Never automatically drop update stashes, even after success. `rescue-local-*` pins the exact object; explicit Git cleanup remains available. Only a real Git conflict invokes the reviewed resolver; filenames create no policy. Internal materialization/rollback reset without interactive confirmation; the generic owner-facing Restore retains its confirmation.
- Record restoration intent in the existing transaction BEFORE apply. Each completion path consumes restored/preserved/incomplete outcomes; incomplete persistence retains the marker. Interrupted replay neither resets nor reapplies over returned or later work: once storage works, record a handoff of the pinned backup, preserving current files without claiming clean/successful apply. Failure captures rc/stdout/stderr and NUL-separated unmerged paths before verified cleanup; release carries one recovery note to Main/Updates and supervisor events. Unreadable census differs from empty; neither counts successful files or enumerates untracked collisions.
- Ordinary transactions keep schema 1; a `stash_restore` record requires schema 2. New readers accept legacy markers; older strict readers refuse new semantics without reset. Rollback checks out old code before restoration, so interrupted new records can require a capable reader or deliberate recovery: refusal is not automatic recovery. Restart the actual desktop app, Docker/service or direct server, not its browser tab. In-app Restart refuses pending restoration before checkout/reset. Legacy `stash_restored` still means recorded successful apply.
- The resolver stages the full merge, tracked binaries included; review gets exact staged mode/blob/size and parent object IDs. Missing metadata blocks; ordinary commit binary policy is unchanged.
- Managed merge commits require a green full suite on the exact candidate (DEVELOPMENT “The commit gate mirrors the CI split”). Any non-commit resolver terminal rolls back and best-effort preserves the attempt on its deterministic failed-update branch. Recovery needs the fresh rescue, not that branch.
- Fresh rescue precedes every destructive rollback and boot re-materialization. Capture failure is fail-open but durably disclosed, with a transaction pointer; ARCHITECTURE §2 owns the choke point and why pre-update rescue is insufficient.
- Manual Restore uses the same writer fence and pins previous HEAD before reset. Promotion resolves development SHA once for both local QA and remote push.

Tests: `tests/test_update_merge_policy.py`, `test_update_dirty_stash.py`, `test_update_stash_recovery.py` (real Git, crash/replay, consumers, Restart), `test_update_hardening.py`, `test_update_tx_corrupt_quarantine.py`.

Native hosts add no source updater: the launcher hook verifies its installed artifact before core start; post-boot readback precedes finalization. Failure uses existing rollback. Worker self-restart retains incomplete native adoption even when core SHA matches.
